# Planner — Known issues

Problems that are known and not yet fixed, to come back to. When one is decided, its outcome becomes a requirement in the
relevant specification, and it is removed from here.

| ID | Issue | Notes |
|---|---|---|
| `ISSUE-1` | Creating a project or PCB overwrites any existing file of the same name, without warning, as soon as Ok is clicked (`DOC-1`). This loses the existing document. The CLI's `create` commands do the same. | A suggested fix is for the core to refuse to create a document whose file already exists, and for the form to show the error. Not decided. |
| `ISSUE-2` | A PCB in a subfolder of the project is stored with the separator of the system that added it (`PROJPCB-2`), so a project made on Windows may not find that PCB on Linux. | From reading the code, not tested. A PCB directly in the project's folder has no separator, so isn't affected. |
| `ISSUE-3` | The minimum height of a table (`FORM-8`) assumes the default row height of 18 and spacing of 3 (`forms/mod.rs`, `TABLE_ROW_HEIGHT`), so the minimum is wrong if the rows are a different height. | This needs to be dynamic, set at runtime from the egui style in use, likely the body text size, `interact_size` and `item_spacing`. |
| `ISSUE-5` | A project's PCB and Unit assignments tabs number PCBs from 0, for example "`PCB (0)`", while the project explorer and object paths number them from 1, for example "`pcb=1::unit=1`". | Seen in the UI tests. Numbers shown to the user elsewhere count from 1. |
| `ISSUE-6` | The Add phase dialog can't create a new load-out, as its "`...`" button opens a dialog that only chooses an existing file (`PHASE-3`). The user has to create an empty file some other way first. The CLI's `create-phase` just needs a path, and the core creates the file. | From reading the code, the real dialog was not tried. Tests answer the dialog, so they could answer with a file that doesn't exist, and they deliberately don't. Could be fixed with a save dialog, or a "New" button. |
| `ISSUE-7` | A load-out is stored with its absolute path (`PHASE-3`), so after a project's folder is moved its phases still refer to the load-outs in the old folder. PCBs avoid this using a relative path (`PROJPCB-2`). | The stored path is checked by tests, the effect of moving the folder is from reading the code. Not just a GUI change: in the core, `build_phase_load_out_item_map` treats a relative path as relative to the project's folder, while `ensure_load_out` and `store_items` treat it as relative to the current directory. |
| `ISSUE-8` | Adding a phase using a reference that's already used doesn't report an error. It replaces that phase's process and load-out source, and silently keeps its old PCB side. It also starts the phase's state again, which looks like it loses its recorded operations. | Replacing the process and load-out and keeping the side were seen in a test through the GUI, and losing operations is from reading `Project::update_phase`. The CLI uses the same event. The form has a `FUTURE` note that it could validate the reference. |
| `ISSUE-9` | While a phase's "`Placed?`" cell is being edited, clicking the same cell of the next row doesn't finish the edit. Clicking another cell of the row does. So marking several placements row by row takes more clicks than it seems it should. | The clicks were seen failing and working in a test. The likely cause, from the code, is that the editor's three radio buttons make it taller than its row, so it covers the rows below. |
| `ISSUE-10` | "`Remove`" on the Placements tab ignores the phase chosen in "`Phase`". With `top_1` chosen, it removes a selected placement from `bottom_1`. The choice has no effect, but "`Actions`" stays disabled until one is made, so it looks as if it matters. | Seen in a temporary test through the GUI. Either only remove placements from the chosen phase, or don't require a phase for "`Remove`". |
| `ISSUE-11` | "`Apply`" on the Placements tab leaves any selected placement on the other side of the PCB to the phase as it was, with no message. If all of them are on the other side, nothing at all appears to happen. | Seen in a temporary test through the GUI. The core filters them out in `assign_placements_to_phase`, which the CLI's patterns rely on, so a message would most likely come from the GUI. |

IDs are never reused.
